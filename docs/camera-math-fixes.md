# Fixes: Math, Camera and Transform

This document describes the math and logic fixes applied to the raytracer's core classes, in particular the camera behavior and how normals are handled under geometric transformations.

---

## 1. Camera rotation (`Camera::getScreen`)

### The original problem
In the first implementation, `Camera::getScreen()` built the screen plane with the view axis hardcoded to `-Z`. The camera's `rotation` attribute was never used. As a result, changing the camera rotation did not change the direction of the generated rays: the camera always looked the same way.

### The fix
For the camera to look in any direction, the screen plane (the pixels we project through) must rotate *with* the camera.

The process is:
1. **Build a global rotation matrix**: multiply the X, Y and Z rotation matrices using the angles from `camera.rotation`.
2. **Define the screen vectors in local space**: the plane origin, the bottom vector (`bottom_side`) and the left vector (`left_side`) are defined as if the camera were at the origin `(0, 0, 0)` looking toward `-Z`.
3. **Apply the rotation**: multiply these three local vectors by the rotation matrix.
4. **Final translation**: add the camera `position` to the rotated origin to place it correctly in the world.

When the camera rotates, the screen plane now pivots exactly the same way, and the rays generated by `getRayForPixel()` go in the right direction.

## 2. Scale, normals and `transpose()`

This is one of the classic pitfalls of 3D rendering.

### Why are normal vectors special?
A normal vector gives the direction perpendicular to a surface. Unlike points or direction vectors (such as a light ray), **normals do not behave the same way under non-uniform transformations (asymmetric scale)**.

Picture a perfect circle with a normal pointing up at 45°. If we stretch the circle along X only (Scale X = 2.0), it becomes an ellipse and the surface flattens.
* If we apply the same scale matrix to the normal, it stretches along X and **tilts the wrong way**. It is no longer perpendicular to the ellipse surface.

### The math rule
Mathematically, normals are "covectors". For a normal to stay orthogonal to its surface after a transformation $M$, it must not be multiplied by $M$ but by **the transpose of the inverse of $M$**: $(M^{-1})^T$.

### Implementation in `Transform::getNormal()`
In the Decorator pattern (`Transform`), the object holds two matrices:
* `_localToWorld`: the base transformation matrix $M$.
* `_worldToLocal`: its inverse $M^{-1}$.

To transform a point or direction vector from local to world space, we use `_localToWorld`.
But to **transform a normal** from local to world space, the formula requires $(M^{-1})^T$.
Since $M^{-1}$ is already computed (`_worldToLocal`), we only need **its transpose**.

That is why `Matrix4x4::transpose()` was added, and `Transform::getNormal()` is now written as:

```cpp
Vector3D Transform::getNormal(const Point3D& point) const {
    // 1. Bring the point back into local space
    Point3D localPoint = _worldToLocal.transformPoint(point);
    
    // 2. Get the normal of the base primitive (e.g. the perfect sphere)
    Vector3D localNormal = _wrapped->getNormal(localPoint);
    
    // 3. Bring the normal back to world space using the transpose of the inverse
    return _worldToLocal.transpose().transformVector(localNormal).normalize();
}
```

With this fix, when a primitive is scaled (e.g. a sphere turned into an oval), lighting computations (which depend on normals) stay physically correct, with no distorted shading.

## 3. Other minor fixes
* **`Matrix4x4::transformRay`**: a critical bug transformed an uninitialized ray (`Ray r;`) instead of the parameter. It now uses the `ray` parameter and normalizes its direction.
* **Initialization order**: fixed strict warnings (`-Werror`) in the `Transform` constructor.
* **Includes**: fixed relative paths to the math headers in the interfaces (`IPrimitive.hpp`, `HitInfo.hpp`).
